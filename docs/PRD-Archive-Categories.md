# 归档分类功能 PRD

## 1. 文档信息

- 产品：今天藏什么（Storing）
- 功能：归档分类与 AI 受控分类
- 版本：v1.0
- 日期：2026-08-13
- 适用端：Web、Web 移动端、Android、API

## 2. 背景与问题

当前流程是“收集文章 → 收件箱 → 判断价值 → 归档”。归档页已有来源信息，但缺少稳定的主题组织方式。此前 AI 可以自由生成分类，导致分类数量失控，出现一篇文章一个分类的问题。

本功能要让 AI 提供自动化，同时保证分类体系由用户控制：AI 只能从用户预设分类中选择，无法自行创建分类；无法判断的文章进入“待整理”，用户可随时修正。

## 3. 产品目标与非目标

### 3.1 目标

1. 归档文章拥有一个稳定、可导航的主分类。
2. 收件箱保持快速收集和筛选，不强制分类。
3. AI 分类结果可解释、可纠正、可追踪。
4. 分类、标签、来源职责清晰，并在三端保持一致。
5. 兼容已有文章、来源、标签和归档状态。

### 3.2 非目标

- 第一版不支持 AI 自动创建分类。
- 第一版不支持父子层级分类。
- 第一版不把来源转换为分类。
- 第一版不新增独立的“分类入库页”。

## 4. 核心概念

| 信息 | 定义 | 约束 |
| --- | --- | --- |
| 分类 | 文章长期归属和归档主导航 | 每篇归档文章一个 |
| 标签 | 细粒度主题和关键词 | 每篇可多个 |
| 来源 | 文章来自的公众号、网站或客户端来源 | 独立字段，可筛选 |
| 待整理 | 无法可靠判断时的系统兜底分类 | 不可删除 |

示例：分类“编程开发”，标签“PostgreSQL、索引、性能优化”，来源“postgresql.org”。

## 5. 用户流程

### 5.1 收件箱

1. 文章收集后进入收件箱，默认不要求分类。
2. 用户阅读、收藏、删除或点击归档。
3. 归档时触发分类判断：优先使用用户已选择的分类，否则使用 AI 推荐。

### 5.2 归档

- AI 置信度大于等于 0.75：自动使用推荐分类。
- AI 置信度 0.50 至 0.74：使用推荐分类并标记“需要确认”。
- AI 置信度低于 0.50：进入“待整理”。
- 用户手动选择分类后，结果来源标记为 `user`，优先级高于 AI。

### 5.3 分类建议

当现有分类无法覆盖一批文章时，系统可以生成“建议新增分类”，但必须由用户确认后才创建。

## 6. 分类管理页

入口：`设置 → 分类管理`。

### 6.1 分类列表

显示分类名称、文章数量、启用状态、排序和最近修改时间。固定显示“待整理”。

### 6.2 新建/编辑分类

字段：名称、说明、适合收录的内容、不适合收录的内容、示例文章、显示颜色、启用状态。说明和示例会作为 AI 分类上下文。

### 6.3 分类操作

- 调整排序
- 启用/停用
- 合并分类
- 查看分类文章
- 查看 AI 建议新增分类

删除或合并分类时必须选择目标分类，不能删除文章。系统分类“待整理”不可删除。

## 7. 三端界面要求

### 7.1 Web

- 归档左侧默认显示“分类”面板，支持与“来源”面板切换。
- 分类面板包含“全部文章、待整理、正式分类”和文章数量。
- 顶部保留搜索、来源筛选、标签筛选和排序。
- 卡片层级：标题 → 分类 → 标签 → 来源/时间/状态。
- 分类使用低饱和度主题色；来源使用弱化灰色。

### 7.2 Web 移动端

- 顶部使用可横向滚动的分类 Tab：全部、待整理和正式分类。
- 排序保留在列表工具栏。
- 来源和标签放入筛选抽屉。
- 卡片显示“分类 · 来源”、标题、摘要、少量标签和时间，避免信息拥挤。

### 7.3 Android

- 顶部使用分类横向 Tab。
- 排序和“全部来源”保留为独立筛选控件。
- 来源筛选使用 Bottom Sheet。
- 卡片显示封面、分类 · 来源、标题、摘要、标签和更多菜单。
- 更多菜单支持修改分类、批量移动、修改标签、移回收件箱和删除。

### 7.4 详情页

Web 与 Android 复用统一详情逻辑。标题下方展示当前状态和分类；来源放在文章信息区。支持修改分类、修改标签、归档、移回收件箱和查看 AI 分类理由。

## 8. AI 与接口契约

AI 必须返回结构化结果，只能选择传入分类 ID：

```json
{
  "category_id": "programming",
  "confidence": 0.91,
  "reason": "文章主要讨论 PostgreSQL 索引和查询性能"
}
```

禁止返回新的分类名称。服务端必须校验 `category_id` 属于当前用户启用分类或系统分类。

建议接口：

- `GET/POST/PATCH/DELETE /api/v1/categories`
- `POST /api/v1/articles/:id/classify`
- `PATCH /api/v1/articles/:id/category`
- `POST /api/v1/articles/bulk-category`
- `POST /api/v1/categories/reorder`
- `POST /api/v1/categories/merge`

文章列表支持 `categoryId`、来源、标签和排序筛选。

## 9. 数据要求

新增 `categories` 表，字段包括 `id`、`user_id`、`name`、`description`、`include_examples`、`exclude_examples`、`color`、`sort_order`、`is_active`、`is_system`、时间字段。

`article_metadata` 增加 `category_id`、`category_source`、`category_confidence`、`category_reason`、`category_review_status`、`category_model_version`。已有 `ai_category` 保留用于兼容，后续不再作为主分类来源。

## 10. 迁移策略

1. 为每个用户初始化“待整理”。
2. 现有归档文章先迁移到“待整理”，不删除任何原始数据。
3. 提供批量 AI 分类任务，结果标记为“需要确认”。
4. 用户确认或修改后变为正式分类。
5. 原有来源、标签、收藏、发布和文章正文全部保留。

## 11. 验收标准

- AI 永远不能创建预设列表之外的分类。
- 收件箱文章可以没有分类；归档文章必须有分类。
- 低置信度文章进入“待整理”。
- 用户修改后分类来源为 `user`，不会被后续自动分类覆盖。
- Web 默认按分类浏览，来源仍可独立筛选。
- Web 移动端和 Android 分类可横向切换，来源通过独立筛选访问。
- 分类、来源、标签在卡片和详情页层级清晰，不发生文字或控件重叠。
- 旧文章、来源、标签和归档状态全部可正常访问。
- 分类删除、停用和合并不会删除文章。

## 12. 成功指标

- 归档文章分类覆盖率达到 100%。
- “待整理”文章占新增归档文章比例可被持续观测。
- 人工改分类率逐步下降。
- 用户能在三次点击内按分类找到目标文章。
- 分类总量保持在用户可维护范围，默认建议 5 至 15 个。
